# Database: Prisma schema, migrations & seed

Spec: `docs/spec/06-database.md` (§6.1 principles, §6.3 data dictionary, §6.6 migrations).

## Files

| Path                       | Purpose                                                         |
| -------------------------- | --------------------------------------------------------------- |
| `schema.prisma`            | 18 models (camelCase) mapped to snake_case MySQL tables/columns |
| `migrations/`              | SQL migrations, committed to Git, applied in order              |
| `seed/index.ts`            | Seed entry (`--demo` flag → demo data, P17)                     |
| `seed/base.ts`             | Idempotent base seed: 12 default categories, 15 tip templates   |
| `../prisma.config.ts`      | Prisma CLI config: loads root `.env`, migrator URL, shadow DB   |
| `../src/generated/prisma/` | Generated client (git-ignored, `npm run db:generate`)           |

## Accounts

- **Migrations** run as `cc_migrator` (`DATABASE_MIGRATOR_URL`, full rights on `campus_coin` and the shadow DB `campus_coin_shadow`).
- **App and seed** run as `cc_app` (`DATABASE_URL`, SELECT/INSERT/UPDATE/DELETE only).

## Commands (PowerShell, from the repo root)

```powershell
docker compose up -d                       # MySQL, Redis, Mailpit
npm run db:migrate -w backend              # apply pending migrations (dev)
npm run db:seed -w backend                 # base seed (safe to run repeatedly)
npm run db:reset -w backend                # DROP + recreate DB, apply all migrations, seed
npm run db:studio -w backend               # browse data
npm run db:deploy -w backend               # production: apply migrations only (after a backup)
```

## Creating a migration

1. Edit `schema.prisma`.
2. Create the SQL **without applying it**:
   ```powershell
   cd backend; npx prisma migrate dev --create-only --name <short_snake_name>
   ```
3. Review/edit `migrations/<timestamp>_<name>/migration.sql` by hand when Prisma cannot express something:
   - `CHECK` constraints (e.g. `amount > 0`) – Prisma does not model them.
   - Table collation: change `utf8mb4_unicode_ci` to **`utf8mb4_0900_ai_ci`** on every `CREATE TABLE`.
   - Data backfills for expand/contract steps.
4. Apply: `npm run db:migrate -w backend`, then run the tests.
5. Commit schema + migration together.

Because CHECK constraints and collation are invisible to Prisma, hand edits never cause schema drift.

## Rules

- **Forward-only.** Never edit or delete a migration that has been applied anywhere (another dev machine,
  staging, production). Fix mistakes with a new migration.
- **Breaking changes use expand → migrate → contract:**
  1. _Expand_: add the new column/table (nullable or with default); the app writes both old and new.
  2. _Migrate_: backfill data; switch reads to the new structure.
  3. _Contract_: in a later release, drop the old column/table.
     Never rename or drop a column in the same release that stops using it.
- Production: `migrate deploy` only, always after a backup (spec §6.6). Never `migrate dev`/`reset` there.
- Never run the `--demo` seed on real production data.

## Design notes

- **UUID v7** primary keys (users, transactions, import_batches, refresh_tokens) come from Prisma's
  `@default(uuid(7))` – generated by the client, stored as `CHAR(36)`.
- **`categories.owner_key`**: the spec wants a generated column `COALESCE(user_id,'SYSTEM')` so that
  `UNIQUE(owner_key, type, name)` also covers system categories (NULL user_id). Prisma cannot model
  generated columns, so it is a plain column the service sets to `userId ?? 'SYSTEM'`, guarded by the
  CHECK `chk_categories_owner_key`. MySQL only allows that CHECK because the `categories.user_id` FK has
  no cascading action (`ON DELETE RESTRICT ON UPDATE RESTRICT`).
- **Admin MFA recovery codes**: `users.mfa_recovery_codes` JSON array of hashes.
- **CSV import preview** rows live in Redis (24 h TTL), not in MySQL.
- `@db.Date` columns (txn_date, month, period…) are read/written as UTC-midnight `Date`s – use
  `toDbDate` / `fromDbDate` from `src/lib/dates.ts`.
- The Prisma AI-safety guard blocks `migrate reset` when run by an AI agent unless the owner consents.
